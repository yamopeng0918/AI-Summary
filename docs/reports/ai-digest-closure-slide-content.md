## 4. 三來源完整處理流程

### 畫面文字

公開網址 → 來源辨識 → 取得文字

一般網頁：擷取正文

YouTube：字幕優先；無可用字幕才轉錄音訊

Bluesky：取得公開單篇貼文

AI 摘要 → 分類 → Schema 驗證 → JSON 儲存

### 視覺配置

原生可編輯流程圖。僅「取得文字」階段分成三路，之後匯回共同主幹。建置與部署標為後續獨立操作，避免暗示 add 自動部署。

### 講者備註（50 秒）

流程從公開網址開始。系統先辨識來源，再選擇對應的解析器。網頁擷取正文，Bluesky 取得單篇貼文；YouTube 優先使用字幕，沒有可用字幕才進行音訊轉錄。三種來源取得文字後，就進入相同的摘要、分類、驗證和保存流程。這裡有一個重要邊界：Schema 驗證通過，才可以寫入 JSON。保存後，使用者再執行網站建置和部署；新增摘要不會自行把內容推到遠端。這讓資料處理和公開發布可以分別檢查，也方便定位失敗發生在哪個階段。

## 6. 系統架構與技術選擇

### 畫面文字

本機 Python CLI：擷取 → 摘要 → 分類 → 驗證與保存

獨立解析器｜共同資料契約｜JSON 儲存

Astro：只讀取已驗證且 published 的資料

公開前端不持有 API 金鑰

### 視覺配置

以原生可編輯架構圖呈現本機、資料檔、公開網站三層，標出憑證停留在本機的邊界。與前頁流程圖區別，重點放在責任分工。

### 講者備註（45 秒）

技術上，我用 Python CLI 處理來源擷取、AI 摘要與分類，因為資料處理和模型可以在同一個環境中整合。各個解析器只負責取得內容，不直接呼叫摘要服務，也不寫入摘要檔。摘要服務和分類器也各自維持單一責任。儲存層負責驗證與保存，Astro 則只讀取合法且已發布的資料。這樣做的好處，是某個平台出問題時，可以在自己的解析器中處理；同時，公開網站不需要金鑰，也不直接呼叫 AI 服務，安全邊界更清楚。

## 7. 分類模型與量化證據

### 畫面文字

91.67% Accuracy

0.9179 Macro F1

最大類基準 16.67%｜Accuracy 高出 75 個百分點

180 筆人工審核資料，六類各 30 筆

固定切分：訓練 144／測試 36；seed 42

### 視覺配置

大型 Accuracy 數字搭配原生可編輯橫條圖，比較模型 91.67% 與基準 16.67%；同一條 0–100% 軸線。附上樣本數，不將 Macro F1 誤標為 Accuracy。

### 講者備註（50 秒）

分類部分採用 TF-IDF 搭配 Logistic Regression。資料集有一百八十筆人工審核資料，六個類別各三十筆，使用固定的隨機種子，分成一百四十四筆訓練資料和三十六筆測試資料。測試集三十六筆中，三十三筆分類正確，Accuracy 是百分之九十一點六七；Macro F1 是零點九一七九。若全部猜同一個最大類別，基準只有百分之十六點六七，因此模型高出七十五個百分點。不過這是固定小型測試集的結果，不能直接保證所有未來內容都有相同準確率。保留評估報告與混淆矩陣，就是為了讓結果可以重現和檢查。

## 8. 跨來源整合挑戰與解法

### 畫面文字

文字取得方式不同 → 獨立解析器與共同資料契約

YouTube 無可用字幕 → 音訊轉錄與暫存清理

公開部署的資料風險 → Schema 驗證、敏感資訊掃描、部署 gate

### 視覺配置

三列「挑戰 → 解法」，採開放式文字排版，不做密集卡片。以珊瑚紅標示挑戰關鍵詞。

### 講者備註（45 秒）

整合時，我遇到三個主要挑戰。第一是來源差異，處理方式是把解析器獨立出來，讓後面的流程只面對共同資料契約。第二是影片不一定有字幕，因此加入音訊轉錄，並在結束或失敗時處理本機及遠端暫存清理。第三是公開部署的風險：資料不完整或包含敏感資訊，都不應該出現在網站上。所以保存前有 Schema 驗證，部署前有建置和敏感資訊掃描。這些工作讓我學到，可靠性必須包含失敗時的行為，而不只是成功路徑能夠執行。
